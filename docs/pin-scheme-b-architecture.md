# 置顶功能 A→B 架构设计文档（生产级）

> 文档类型：架构选型与数据一致性设计  
> 项目：SSE Market（软工集市）  
> 范围：主页置顶队列从「帖子表内联」迁移到「独立队列表」  
> 原则：约束驱动决策；本文件不包含实现代码  
> 关联：`docs/pin-feature-design-report.md`（业务约束与方案对比）

---

## 0. 决策摘要（先读）

| 问题 | 结论 |
|------|------|
| 当前是什么 | **方案 A**：`posts.is_pinned / pinned_at / pinned_expires_at` |
| 目标是什么 | **方案 B**：独立队列表（**MySQL `pin_queue` 为权威源**） |
| Redis 角色 | **缓存加速层**，不是权威队列；不做「仅 Redis ZSET」主存 |
| 一致性模型 | 写穿 MySQL → 失效 Redis/世代号；读允许短暂空窗，不允许脏置顶长期存活 |
| 失败恢复 | Cron 对账 + 读路径过滤过期 + 可回滚到 A（保留 posts 字段窗口） |

---

## 1. 当前 A 方案的问题

### 1.1 A 方案本质

置顶状态是帖子实体的附属属性：

```
posts 行 = 内容实体 ∪ 置顶队列语义
```

首页通过「另查置顶子集 + 主列表排除 ID」展示，但**写模型仍绑在帖子行上**。

### 1.2 结构性问题（与业务 bug 的映射）

| ID | 结构性缺陷 | 已观测后果 | 为何修字段/修 Cron 仍治不好「架构债」 |
|----|------------|------------|----------------------------------------|
| A1 | **生命周期耦合** | 删帖/改分区/改隐私时，置顶态与帖子行同一行；易漏联动 | 业务规则「置顶是队列操作」，却用「改帖字段」表达 |
| A2 | **队列语义弱** | 顺序靠 `pinned_at` 挤在帖子表；全站容量靠应用 COUNT | 无独立队列实体，难表达多 scope（多版面） |
| A3 | **审计缺失** | 出队即清空三字段，无法回答「谁何时置顶/取消」 | 生产运营与纠纷需要事件流，A 无天然位置 |
| A4 | **索引与扫描形态差** | `ListPinned` 条件打在大表 `posts` 上 | 置顶基数 ≤5，却与百万级帖表同表竞争索引设计 |
| A5 | **一致性补丁化** | 曾出现「过期仍 is_pinned=1」「角标假置顶」 | 依赖读时计算 + Cron 回写；补丁能止血，但状态机仍分散 |
| A6 | **扩展天花板低** | 多分区置顶、运营手动调序、A/B 运营位 | 继续堆 posts 列会变成宽表 + 更多特殊 SQL |

### 1.3 A 方案「已经够用」的边界

在以下条件同时成立时，A 是合理的：

- 全局有效置顶 ≤ 5  
- 仅一个 Feed 面（主页）  
- 无审计/无运营调序需求  
- 团队希望零新表  

**当前产品方向已明确要「生产级队列 + 可演进」**，因此越过了 A 的舒适区。

### 1.4 A 方案不能用「再加几列」解决的原因

| 诉求 | 加列能否解决 | 说明 |
|------|--------------|------|
| FIFO 队列 | 部分能 | 已有 `pinned_at`，但队列仍不是一等公民 |
| 多版面 | 差 | 需要 `scope` 维度；posts 行无法优雅表达「同帖多队列」 |
| 审计 | 不能 | 必须另表；既已另表，队列本体也应独立 |
| 删帖联动 | 差 | 仍要记得清帖字段；独立表可用显式出队 + 事件 |

## 2. 为什么选择 B 方案

### 2.1 选型命题

把置顶从「帖子属性」升级为「**有界、有 TTL、可审计的队列资源**」。

### 2.2 与硬约束的对齐

| 硬约束 | B 如何对齐 |
|--------|------------|
| 全站 5 条 | `COUNT(pin_queue WHERE scope=home AND expire_at>now) < 5` 入队闸门 |
| 每人 1 条 | `COUNT(... owner_user_id=?) < 1` |
| FIFO | `ORDER BY enqueue_at ASC, post_id ASC` |
| 仅主页 | `scope='home'` + 业务校验 `partition=主页` |
| 用户 1h / 管理员 30d | `expire_at` 入队时写入 |
| 与普通帖不乱序 | API 仍返回 `{pinned, posts}`；`posts` 排除队列中的 `post_id` |

### 2.3 相对 A 的不可替代收益

1. **领域正确**：队列操作（enqueue/dequeue/expire）有独立存储边界。  
2. **可审计**：`pin_events` 可回答运营与客服问题。  
3. **可扩展**：`scope` 支持未来「分区置顶 / 活动页置顶」而不污染 posts。  
4. **查询隔离**：置顶读写落在小表（行数约 O(活跃置顶)），不依赖 posts 宽表过滤。  
5. **删帖/改分区治理清晰**：删帖 = 出队事件；改非主页 = 拒绝入队或强制出队。

### 2.4 为什么现在切（而非继续打补丁）

- 产品已引入 FIFO、全站上限、管理员 TTL、发帖勾选置顶等规则 → **规则复杂度已超过「三字段」模型**。  
- 后续若要运营后台/审计，必然新增表；提前切 B 避免「posts 字段 + 队列表」长期双权威。

## 3. B 方案优缺点

### 3.1 优点

| 优点 | 生产含义 |
|------|----------|
| 队列一等公民 | 入队/出队/过期状态机清晰，可单测、可监控 |
| 小表高性能 | 活跃行 ≤5（home），查询与锁竞争极低 |
| 审计自然 | `pin_events` 与队列解耦，出队不丢历史 |
| 多 scope 扩展 | 新 Feed 加 scope，不改 posts schema |
| 回滚窗口可控 | 过渡期可保留 posts 内联字段只读/双写 |

### 3.2 缺点与固有风险

| 缺点 | 影响 | 是否可接受 |
|------|------|------------|
| **双实体一致性** | 帖删除后队列表可能残留 | 必须：删帖出队 + 定时对账 |
| **读路径多一次关联** | 先取 `post_id` 列表，再取帖详情 | 可接受：最多 5 ID |
| **迁移成本** | 存量导入 + 读写切换 + 验证 | 一次性成本 |
| **运维多一张表** | 备份/监控增加 | 可接受 |
| **若误用 Redis 作权威** | 重启/闪断丢队列 | **本设计明确禁止**（见 §5） |

### 3.3 B 的两种子形态（必须二选一）

| 子形态 | 权威存储 | 适用 |
|--------|----------|------|
| **B-MySQL（推荐）** | `pin_queue` 表 | 当前团队、当前流量、强一致入队闸门 |
| B-Redis-ZSET | Redis ZSET | 超高 QPS、可接受短暂不一致、有专职 Redis 运维 |

**结论预告**：选 **B-MySQL 权威 + Redis 可选缓存**，不是 B-Redis 权威。

## 4. 数据流设计

### 4.1 领域对象

```
PinQueue(scope, post_id, owner, source, enqueue_at, expire_at)  // 当前有效
PinEvent(scope, post_id, actor, action, source, detail, ts)     // 不可变流水
Post                                                          // 内容实体，不含队列权威态
```

### 4.2 读路径（首页 Browse）

```
Client
  → POST /api/auth/browse (home)
      → 1) 读置顶 ID 列表（权威：MySQL pin_queue；可选：Redis 缓存命中）
           WHERE scope=home AND expire_at > now
           ORDER BY enqueue_at ASC, post_id ASC
           LIMIT 5
      → 2) 按 ID 顺序加载 Post + 可见性过滤（私密帖仅作者）
      → 3) 普通列表 ListBrowse，ExcludePostIDs = 置顶 ID
      → 4) 返回 { pinned, posts, total }
```

**不变式**：

- `pinned ∩ posts.post_id = ∅`  
- `len(pinned) ≤ 5`  
- `pinned` 顺序 = 入队先后（FIFO）  
- 角标 `isPinned` =「该 post_id 是否在活跃 pin_queue」而非 posts 字段

### 4.3 写路径：用户入队

```
pinPost(post_id, user)
  → 校验：登录、作者、partition=主页
  → 校验：同帖未在队；owner 活跃数 < 1；scope 活跃数 < 5
  → 事务（建议）：
       INSERT pin_queue(... enqueue_at=now, expire_at=now+1h)
       INSERT pin_events(action=enqueue, source=user)
  → 失效：InvalidateHomeBrowse + DEL redis pin cache（若有）
  → 返回成功
```

拒绝时写 `pin_events(action=reject, detail=原因)`（可选但利于运营）。

### 4.4 写路径：出队

| 触发 | 动作 |
|------|------|
| 用户/作者取消 | DELETE pin_queue + event=dequeue |
| 管理员取消 | 同上，source=admin |
| TTL 过期 | Cron/对账 DELETE + event=expire |
| 删帖 | 强制出队 + event=dequeue/detail=post_deleted |
| 帖改非主页（若允许改分区） | 强制出队 |

### 4.5 与普通 Feed 的边界

置顶**永不**进入「按 post_time 排序的主查询权重」。  
过期出队后，帖自然回到普通流，按原发帖时间排序——这是产品语义，不是 bug。

### 4.6 多 scope 预留（不做过度设计）

当前仅 `scope=home`。  
表与 API 预留 scope 字段；**不实现**多队列产品功能，直到有明确需求。

## 5. Redis 与 MySQL 一致性方案

### 5.1 角色划分（硬规则）

| 组件 | 角色 | 允许存什么 | 禁止存什么 |
|------|------|------------|------------|
| **MySQL `pin_queue`** | **唯一权威（Source of Truth）** | 有效队列全量字段 | — |
| **MySQL `pin_events`** | 审计权威 | 历史事件 | 不参与在线排序 |
| **Redis** | **派生缓存** | `pin:home:ids` → 有序 post_id 列表；可选 TTL 30–60s | 不可作为入队闸门唯一依据 |
| **世代号/首页缓存** | 已有 Browse 缓存失效机制 | 与现网 `InvalidateHomeBrowse` 对齐 | 不单独存置顶真值 |

### 5.2 为什么不用「Redis ZSET 权威」

| 风险 | 后果 |
|------|------|
| Redis 重启/内存淘汰 | 置顶队列丢失或半残 |
| 与 MySQL 帖删除不同步 | 幽灵置顶 ID |
| 入队闸门只看 Redis | 并发下超卖第 6 个名额 |
| 无事务与事件同库 | 审计与队列难原子 |

在当前约束（≤5 条、Browse QPS 未到必须缓存层）下，**权威放 MySQL 的正确性收益 > Redis 权威的延迟收益**。

### 5.3 推荐一致性模式：**Cache-Aside + 写后删除**

```
读：
  1. GET pin:home:ids
  2. miss → SELECT pin_queue → SET pin:home:ids（短 TTL）→ 返回

写（入队/出队/过期清理）：
  1. 事务提交 MySQL 成功
  2. DEL pin:home:ids
  3. InvalidateHomeBrowse()
```

**不采用写后更新缓存**：避免「先更新缓存、DB 失败」或「并发写覆盖错序」。

### 5.4 一致性窗口与用户可见性

| 场景 | 窗口 | 用户可能看到 | 是否允许 |
|------|------|--------------|----------|
| 写成功后缓存未删干净 | 极短（实现应先 DEL 再返回） | 旧置顶列表 | 尽量消灭；TTL 兜底 |
| 缓存 TTL 内漏失效 | ≤ 60s | 略旧 FIFO | **允许**（产品可接受） |
| Cron 未跑、行已过期仍在表 | 读路径必须 `expire_at > now` | 不应看到过期置顶 | **不允许**（读过滤兜底） |
| Redis 全挂 | — | 直读 MySQL | **允许**（降级） |

### 5.5 入队闸门一致性（防第 6 席）

- 闸门计数必须打在 **MySQL**（`SELECT COUNT` 与 `INSERT` 同事务，或依赖 `UNIQUE(scope,post_id)` + 事务内锁定策略）。  
- Redis 计数**不得**作为唯一闸门。  
- 可选优化：事务用 `SELECT ... FOR UPDATE` 锁 scope 哨兵行 / 间隙策略；因 n≤5，简单 `COUNT`+事务重试通常足够。

### 5.6 与现网 Redis 的关系

现网已有 Redis（会话、浏览计数、Feed 世代号等）。  
置顶缓存应：

- 使用独立 key 前缀：`pin:v1:home:ids`  
- 失败降级：Redis 错误 → 忽略缓存，直读 MySQL  
- 不引入 Redis 新集群依赖作为上线前提

## 6. 失败恢复方案

### 6.1 故障分类与处置

| 故障 | 检测 | 自动恢复 | 人工恢复 |
|------|------|----------|----------|
| 入队事务失败 | API 错误率 | 客户端重试；无部分写入 | 查 `pin_events` reject/无 enqueue |
| 入队成功但缓存未删 | 列表短暂旧 | TTL 到期自愈；下次写再 DEL | `DEL pin:v1:home:ids` |
| Cron 停跑 | 无 expire 日志 / 活跃行 expire_at 已过 | 读路径过滤；启动时 ClearExpired | 重启服务；补跑清理 SQL |
| 删帖未出队 | 对账任务发现 post 不存在 | 定时对账 DELETE 孤儿 | 执行对账任务 |
| 双写过渡期 A/B 不一致 | 对账脚本 | 以 `pin_queue` 为准回写或清空 posts 字段 | 切读路径后停止写 A |
| Redis 不可用 | 错误日志 | 直读 MySQL | 修 Redis；无需修队列数据 |
| MySQL 主从延迟（若有） | 读到旧队列 | 置顶读写走主库 | 检查复制 |

### 6.2 对账任务（生产必备）

周期建议：每 1–5 分钟（可与过期清理合并）。

对账规则：

1. **过期行**：`expire_at <= now` → 删除并记 `expire`  
2. **孤儿行**：`pin_queue.post_id` 在 `posts` 不存在 → 删除并记 `dequeue/post_missing`  
3. **非法 scope 帖**：`posts.partition != 主页` 却在 `home` 队列 → 出队  
4. **容量漂移**：活跃数 > 5 → 告警；按 `enqueue_at DESC` 淘汰多余（或人工介入；正常写入闸门下不应发生）  
5. **（过渡期）A/B 差异**：`posts.is_pinned` 与 `pin_queue` 不一致 → 以 B 为准修复 A 或忽略 A

### 6.3 回滚策略

| 阶段 | 回滚动作 |
|------|----------|
| 仅建表未切读 | 停用新代码；表可留 |
| 双写阶段 | 关闭写 B，保留写 A；读回 A |
| 已切读 B | 读切回 A；用最后一次一致快照或 `pin_queue` 回填 posts 字段 |
| 缓存污染 | 批量 `DEL pin:v1:*` + `InvalidateHomeBrowse` |

**前提**：迁移后 **N 天内不删除** `posts` 三字段，作为回滚弹药。

### 6.4 发布开关（建议）

配置项（概念层）：

- `pin.store = mysql_queue | posts_inline`  
- `pin.cache_redis = on | off`  
- `pin.dual_write = on | off`  

灰度顺序：

1. 建表 + 存量导入 + 对账空跑  
2. dual_write=on，读仍 A  
3. 读切 B（小流量/全量）  
4. dual_write=off  
5. 缓存 on

## 7. 最终技术选型结论

### 7.1 选型声明

| 项 | 选定 |
|----|------|
| 目标架构 | **方案 B：独立置顶队列** |
| 权威存储 | **MySQL 表 `pin_queue`** |
| 审计存储 | **MySQL 表 `pin_events`** |
| Redis | **可选 Cache-Aside**，短 TTL，写后删除；**非权威** |
| API 形态 | 保持 `{ pinned, posts }` 双数组（与前端兼容） |
| 过期 | 读过滤（强） + Cron/对账删除（最终一致） |
| 容量闸门 | MySQL 事务内 COUNT（强） |
| 过渡 | 保留 posts 内联字段；可选 dual_write；以 B 为新权威 |

### 7.2 明确不选

| 不选 | 原因 |
|------|------|
| 继续深耕方案 A | 无法干净承载审计与多 scope；与「生产级队列」目标冲突 |
| 方案 C 统一 ORDER BY | 分页与 FIFO 产品语义不匹配 |
| Redis ZSET 权威队列 | 持久化/删帖联动/闸门正确性成本高于收益 |
| 上线即双权威长期并存 | 必出现「以谁为准」事故 |

### 7.3 成功标准（验收）

1. 首页置顶顺序稳定 FIFO；与普通帖无交错排序。  
2. 全站有效置顶恒 ≤5；第 6 次入队被拒绝。  
3. 过期后 ≤60s 出队落库；**立即**不在 `pinned` 返回（读过滤）。  
4. 删帖后队列无孤儿（对账 0）。  
5. Redis 宕机时置顶功能仍正确（仅可能变慢）。  
6. 可在配置开关下回滚读路径到 A（回滚窗口期内）。

### 7.4 架构师结论（一句话）

**用 MySQL 独立队列表做置顶的权威状态机与审计，用现有 API 双通道保证展示不乱序；Redis 只做可丢失的加速缓存，并用写后删除 + 对账任务关闭一致性缺口。**
